# Система навигации и поиска пути (Navigation & Pathfinding System)

Этот документ описывает архитектуру навигации в Scanline Engine, механизмы кэширования, работу через Web Worker и ключевые правила поиска пути, включая последние оптимизации производительности.

## Обзор архитектуры

Система навигации состоит из следующих компонентов:
1. **Scene Walkability (`Scene.ts`)**: Отвечает за определение того, свободна ли точка на сцене, учитывая Walkboxes (зоны для ходьбы), коллайдеры других Entity и триггеры переходов (Exits).
2. **Actor Navigation (`Actor.ts` / `ActorNavigationService.ts`)**: Определяет радиус коллайдера актора и запускает поиск пути.
3. **Navigation Worker (`navigation.worker.ts`)**: Выполняет тяжелые вычисления A* в фоновом потоке, чтобы не блокировать основной поток игры (UI и рендер).
4. **Adaptive Planner (`navigationPlanner.ts`)**: Двухуровневый планировщик маршрутов (Coarse/Fine) с кэшированием достижимости, который оптимизирует поиск точек подхода к интерактивным объектам.

## Как строятся маршруты (Web Worker и Snapshot)

Поиск пути работает асинхронно:
1. Главный поток собирает **Navigation Snapshot** — слепок текущего состояния сцены (walkboxes, границы триггеров, коллайдеры). Snapshot получает уникальный `revision`.
2. Snapshot отправляется в фоновый Worker (`navigation.worker.ts`), где кэшируется в `Map`.
3. Главный поток отправляет `NavigationPlanRequest` в Worker с указанием начальной точки, цели и радиуса взаимодействия.
4. Внутри Worker'а функция `planSnapshotApproach` строит сетку доступности (Walkability Bitmap) и запускает двухуровневый алгоритм A* (Adaptive Pathfinding).
5. Результат возвращается в главный поток.

## Оптимизация поиска пути (A*)

Алгоритм A* (A-Star) опирается на размер ячейки сетки (`gridSize`). 

**Фиксированный размер сетки:**
Размер ячейки сетки жестко зафиксирован в `16` пикселей (`Actor.ts` -> `getRouteGridSize`). 
*Почему:* Ранее сетка вычислялась динамически на основе размера коллайдера персонажа. Для "плоских" коллайдеров (например, 46x2 пикселя) размер сетки мог падать до 4 пикселей. На больших открытых пространствах (длинные коридоры) это приводило к экспоненциальному росту вычислений и алгоритм моментально упирался в лимит безопасности движка (`maxIterations = 50,000`), вызывая лаги (фризы основного потока) и ложные отказы "You are too far away".

## Адаптивное планирование и Кэширование (Adaptive Planner)

Поиск пути использует два прохода для ускорения работы на открытых пространствах:
1. **Coarse Search (Грубый поиск):** Сетка с ячейкой в 4 раза больше обычной (например, 64px). Позволяет быстро прокладывать путь через пустые локации.
2. **Fine Search (Детальный поиск):** Сетка 16px. Применяется, если грубый поиск упирается в мелкие препятствия, или для точной доводки маршрута в узких проходах.

**Кэширование достижимости (Reachability Cache):**
При поиске ближайшей точки подхода к объекту алгоритм может перебирать десятки кандидатов вокруг цели. Чтобы не вычислять путь для каждой точки заново, используются `knownCoarseReachable` и `knownFineReachable` — кэши точек (Set), для которых уже известно, достижимы они или нет в рамках текущего Snapshot'а.
* **Fallback для узких мест:** Если кандидат отсутствует в `knownCoarseReachable`, это означает лишь промах грубого поиска (coarse miss). Алгоритм не возвращает отказ сразу, а **пропускает грубый поиск и переходит к детальному (Fine)** (`skipCoarse = true`), чтобы корректно находить маршруты сквозь узкие пространства.

## Правила взаимодействия NPC и Триггеров переходов (Exits)

### 1. Блокировка NPC физическими переходами
При стандартном блуждании NPC по сцене, система запрещает им случайно выходить за пределы комнаты. 
Метод `Scene.isWalkable` блокирует клетки, в которых находятся физические объекты `Exit`, для всех NPC. 
Однако, если NPC нужно **целенаправленно** покинуть сцену (по приказу Puppet Master'а), при запросе пути передается флаг `ignorePhysicalExits = true`. В этом случае телепорты временно игнорируются при проверке достижимости.

**Кэширование проверок:** Для быстродействия в `Scene.ts` списки физических переходов (`_physicalExitsCache`) и walkboxes (`_walkboxEntitiesCache`) кэшируются и инвалидируются только при изменении структуры сцены (revision changes).

### 2. Типы триггеров Exit (Collider vs Portal)
В редакторе компонент Exit управляется двумя основными флагами, которые определяют логику его активации:
- **Collider:** Активирует переход (телепорт), если Actor пересекает зону триггера своим физическим коллайдером (работает "по касанию").
- **Portal:** Активирует переход только при прямом взаимодействии с областью (например, при клике мышью), при условии, что Actor находится на дистанции доступности (`Reachable`). Также `Portal` визуально меняет курсор мыши при наведении.
- Если **оба флага сняты**, Exit становится "мертвым" для системной навигации и парсера — он сработает только в том случае, если на него будет вручную повешен кастомный скрипт `interact`.

### 3. Скрытие переходов от Парсера
Парсер автоматически игнорирует "технические" границы комнат (края экрана и невидимые переходы). Условием скрытия является **отсутствие свойства `Title`** у объекта (`isNavigationOnlyExit`). 
Объекты-переходы без `Title` не воспринимаются парсером и NPC как интерактивные объекты, что позволяет прозрачно строить сетку локаций без замусоривания командного интерфейса (например, чтобы нельзя было написать `go to exit`, если это просто край экрана).
