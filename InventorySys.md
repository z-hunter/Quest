# Контейнеры

Это объекты сцены с компонентами Inventory и/или Surface, которые могут хранить предметы, т.е.объекты с компонентом Item.

Документ фиксирует текущий реализованный контракт системы контейнеров, parser/world-model семантики вокруг неё и связанных runtime/UI-правил.

## Inventory

Entity могут иметь инвентарь, в котором могут храниться объекты с компонентом Item.
Для этого, Entity должен иметь компонент Inventory, имеющий следующие поля:

- capacity: максимальное количество объектов в инвентаре;
- groups: список group id's (начинаются с #, согласно уже реализованной логике работы с групповыми id в редакторе). Если пуст, то инвентарь может хранить любые объекты. Если задан, то инвентарь может хранить только объекты, которые принадлежат хотя бы одной из этих групп.
- protected: булево значение, определяющее, защищен ли инвентарь от манипуляций со стороны других Actor (по умолчанию false). Если true, то другие Actor не смогут оперировать с предметами этого инвентаря, в том числе видеть содержимое. Полезно, к примеру, для защиты инвентаря NPC от игрока.
- items: список id объектов, которые находятся в инвентаре.

В API добавляются методы для работы с инвентарём, позволяющие добавить предмет (если он подходит по group id и есть свободное место), убрать предмет, проверить наличие предмета, получить список предметов.

Инвентарь персонажа игрока это теперь не частный случай, а работает по этой общей логике. Его команды типа TAKE или DROP теперь вызывают соответствующие методы API.
Главный инвентарь игрока (и любого другого Асtor) это тот компонент Inventory, который присвоен добавлен непосредственно Actor с spatial ralation = "IN" (и он всегда только один). Именно с главным инвентарём работают команды парсера типа TAKE, INVENTORY и тд., и именно содержимое этого контейнера отображается в UI инвентаря, учитывается при выполнении квестов и тд. В общем, главный Inventory Actor-а это то, что мы в в игре называем просто "инвентарь".

## Surface

Любые объекты сцены  могут служить поверхностями для размещения предметов (Item). Для этого, объект должен иметь компонент Surface, имеющий следующие поля:

- capacity: максимальное количество объектов, которые могут быть размещены на поверхности;
- groups: список group id's. Если пуст, то поверхность может принимать любые объекты. Если задан, то поверхность может принимать только предметы, которые принадлежат хотя бы одной из этих групп;
- items: список id предметов, которые находятся на поверхности, вместе с их X/Y координатами на поверхности;

В API предусмотрены методы для работы с поверхностями, позволяющие добавить предмет (если он подходит по group id и есть свободное место), убрать предмет. При добавлении предмета на поверхность он размещается внутри области этого объекта (это может быть прямоугольная область, или многоугольник произвольной формы), прикрепляясь к каким-то случайным X/Y координатам в её предалах. При этом, если на поверхности уже есть предметы, то новый предмет по возможности не должен накладываться на них (только если нет другого выхода). Также предмет не должен выходить за пределы поверхности (если это невозможно, то такой предмет не может быть размещен на поверхности, даже если capacity позволяет).

## Встроенные и внешние контейнеры

### Внешние контейнеры

Компоненты Surface и Inventry могут принадлежать объекту, вложенному в другой объект, причём вложенность может быть многоуровневой. Для модели мира парсера значимы лишь объекты, имеющие поле Title (то есть те, которые в мире игры имеют какое-то название), а объекты без Title это просто технические узлы.
Таким образом, если в объект "Table" имеющий Title,  вложен объект "table surface", со spatial relation "ON" и  не имеющий Title, то с точки зрения парсера это просто поверхность, принадлежащая объекту "Table" с spatial = "ON", принимающая предметы, которые должны находиться НА столе, напр. по команде "PUT Key ON TABLE".
Если в стол вложен ящик стола, который также имеет Title, и в нём наодится что-то без Title, например Switch, в котором находится такая же безымянная поверхность, то поверхность считается принадлежащей ящику стола, поскольку это первый в иерархии родитель с Title.  
Такой подход позволяет гибко задавать разные контейнеры для одного объекта, в том числе полигональные поверхности, не совпадающие с формой и координатами своего "родителя" (напр. область под столом, куда можно положить предмет, и тд.).

### Встроенные контейнеры

Можно использовать и более простой подход -- компоненты Surface и Inventory могут принадлежать непосредственно объекту, имеющему Title, и в этом случае они просто добавляются к нему, без создания дополнительных технических узлов.
Для этого, компонентам Surface и Inventory объектов с Title нужно добавить поле "spatial relation" (по умолчанию "IN"), которое будет указывать на тип spatial отношения к объекту, которому они принадлежат. При этом, данное поле доступно в UI редактора только у объектов с Title, поскольку для безымянных узлов иерархии оно бессмысленно и должно игнорироваться.
Объект может иметь несколько встроенных контейнеров, но только по одному для каждого возможного типа spatial relation (не может быть двух контейнеров "IN" или "ON" и тд.).

## Пространственные отношения предметов в Inventory

Мы меняем реализацию компонента Inventory так, что находящиеся в них предметы теперь участвуют в иерархии сцены и видны там как дочерние объекты своих контейнеров (это относится и к предметам в инвентаре у игрока). Они имеют spatial relation "IN".
Предметы, находящиемя в каком-то инвентаре, исключены из рендеринга и игре не отображаются. В панели иерархии в редакторе они видны, но имеют другой цвет, похожий на тот, что у disabled объектов, однако без перечёркнутой иконки как у disabled.  Таким образом, если надо включить предмет в инвентарь или исключить его оттуда -- это можно сделать прямо в редакторе.

При этом для parser/text layer важно не отношение предмета к самому inventory-узлу, а spatial relation inventory-слота относительно его значимого владельца. Например, если у шкафа есть built-in Inventory с relation `BEHIND`, а книга технически находится как `IN`-ребёнок шкафа, то в текстовом слое книга считается находящейся `BEHIND the Cabinet`.

Команды парсера типа TAKE FROM или PUT INTO работают с внешним (по отношению к персонажу игрока) инвентарём как с IN контейнером, если Inventory не имеет свойства Protected. В противном случае он недоступен в текстовом слое игры (за исключением случая, когда это Inventory самого игрока).
Люой Actor может оперировать своими контейнерами, даже если они protected.

## Пространственные отношения без контейнеров

Поскольку любые объекты могут быть вложены друг в друга с пространственным отношением (spatial), это можно сделать без использования контейнеров, прямо в редакторе сцены, или через скриптовое API.
Такие предметы обрабатываются пространственное моделью в игре точно так же, как и содержащиеся в контейнерах, с той разницей, что они могут быть лишь взяты или использованы Actor'ом, но не могут быть помещены без контейнеров. Например, если под стулом лежит ключ, но никакого контейнера с spatial relation "UNDER" у стула нет, то ключ можно увидеть через LOOK UNDER CHAIR, можно взять через TAKE, но нельзя положить обратно под стул, так как для этого нет контейнера.

## Операции с контейнерами

Контейнеры это объекты, имеющие в себе общедоступные компоненты Inventory (не protected) и/или Surface и благодаря этому позволяющие игроку помещать в себя предметы, а также брать их оттуда.
Команды PUT/DROP должны поддерживать опциональное указание целевого объекта, и указание пространственного отношения к нему (напр. PUT key UNDER the table, или TAKE key FROM the drawer). При этом:

1. Игра должна проверять, существет ли соответствующий контейнер, то есть объект с Inventory/Surface с указанным spatial relation по отношению к целевому объекту, а также не заблокирован ли он (напирмер, ящик может быть закрыт через Switch) и поддерживает ли операции с этим конкретным предметом (подходит ли Group ID, помещается ли предмет в Surface по размеру и тп.).  
2. Если при взятии объекта  с указанием целевого объекта/spatial relation, можно идентифицировать какой из подходящих предметов имеется ввиду, парсер не должен запрашивать лишнего уточнения у игрока. Например, если один карандаш лежит на столе, а другой в ящике стола, то команда TAKE pencil FROM the drawer должна идентифицировать как целевой предмет именно карандаш в ящике.

# Невидимые и недоступные объекты

## Компоненты блокировки

В игре есть компонент `Blocker`, который работает как всегда закрытый `Switch`.
`Blocker` и `Switch` имеют свойство `transparent`. Если оно установлено, то объект позволяет видеть объекты, находящиеся внутри него. По умолчанию оно не установлено.
Также они имеют свойство `blocked spatial relation`, позволяющее указать какие именно объекты он блокирует. По умолчанию оно равно `IN`. В список включены `IN`, `ON`, `UNDER`, `BEHIND`, а также `NONE`, если блокер никого не блокирует (пример: технический `Switch`, который только переключает объекты, но в семантическом плане не влияет на них).

## модель

C точки зрения текстовой (семантической) модели игры значимым объектом считается лишь объект, имеющий поле Title. Только такие объекты, имеющие названия, существуют для текстового слоя как отдельные сущности.

Skope сцены включает в себя три разновидности объектов:

- Видимые
- Заблокированные
- Находящиеся рядом

По умолчанию все значимые объекты в сцене видимы и доступны для игрока.

Блокирующие компоненты (Blocker и закрытый Switch) позволяют заблокировать видимость и доступность объектов, вложенных в их родительский объект по заданному spatial relation. Например, если задано "IN", то блокируется то, что внутри родительского объекта.
Если блокирующий объект прозрачен, то он блокирует лишь доступность, но не видимость.  Switch блокирует лишь в закрытом состоянии, Blocker - всегда.

Заблокированные объекты недоступны для взаимодействия.

Объектам с Title добавляется поле "hidden" (есть в UI только если имеется Title), которое может принимать след. значения:

- false (default): обычное поведение объекта
- lookable: будет невидимым до тех пор, пока игрок не "посмотрит" на него, включая нажатие мыши с выводом названия в консоль, а также вывод команды LOOK (Напр: LOOK UNDER TABLE --> Under the table you see a Key )
- examinable: будут невидимы до тех пор, пока не будут выданы командорй EXAMINE

## Взаимодействие парсерных команд с контейнерами и объектами

Персонаж игрока это Actor с установленным соответствующим свойством. Соответственно, всё что может делать игрок, может на самом деле делать любой Actor. Если во время игры в качестве персонажа игрока будет установлен другой Actor, мы увидим его инвентарь и будем управлять им с помощью команд.

Команды типа TAKE рнаботают с инвентарем и поверхностями (из собственноого инвентаря, естественно, взять предмет нельзя, т.к. он уже взят, его можно только оттуда выбросить).
Стандарная команда PUT/DROP <item> позволяет выложить предмет из инвентаря. В ней можно указать предмет, цель куда класть, а также тип spatial отношения к цели (напр. PUT key UNDER THE TABLE), в этом случае в качестве цели ищеться поверхность, имеющая такое spatial отношение к указанному объекту. Без уточнения цели команда пытается положить указанный предмет (если он есть в инвентаре) на ближайшую к персонажу поверхность, с которой он может быть размещен (с учетом group id и capacity). Положить можно только на поверхность, доступную для персонажа (которую он может видеть и которая при этом не заблокирована и находится рядом с персонажем, по той же логике, что  комаде TAKE или EXAMINE).
 При этом, если открыта Subscene, то в первую очередь кандидатами на цель должны рассматриваться поверхности из Subscene.  Нужно также предусмотреть сообщения о том, что предмет положить невозможно с указанием причины (нет такого места ).
Команда PUT/DROP также может использоваться с предметами, имеющими инвентарь. Например: PUT cassete INTO tape recorder (INTO = IN). В этом случае, предмет размещается уже не на поверхности, а в инвентаре  объекта-контейнера, если, конечно, это возможно соглавно выше описанным правилам. Команда может брать source-item не только из инвентаря, но и прямо из nearby scene item, если и source, и target доступны персонажу. На этот случай также нужны текстовые сообщения про успешность/неуспешность операции.
Положить в контейнер персонаж игрока может только если тот видим и доступен для него. Если же контейнер находится в Subscene, то достаточно лишь того, что он виден.

Если parser запрашивает уточнение для `PUT`, follow-up ответ игрока должен продолжать исходную команду, а не превращаться в новую отдельную команду без исходной цели.

Если целевой объект размещён в инвентаре персонажа, он всегда видим и доступен для опереаций (если не disabled).

Если объект доступен и находится рядом, его можно поднимать, использовать, делать EXAMINE, и даже делать PUT не помещая себе в инвентарь. Например: на столе лежит кассета и стоит магнитофон. Если игрок подойдёт к столу, он может сразу поместить (PUT) кассету в магнитофон без предварительного TAKE.

Не находящиеся радом объекты Actor (включая персонажа игрока) может только рассматривать (LOOK).  Это не касается предметов, имеющих установленное свойство "Ignore distance" в компоненте Item.

Никакие команды не должны оперировать с disabled объектами. С точки зрения игры таких объектов не существует.

## Отображение инвентаря игрока

Во время игры предметы из инвентаря игрока отображаются за пределами игрового экрана, справа от него, в той области, где в в редакторе сцены отображается правая панель. При этом, на них не распространяется CRT фильтр и низкое разрешение игрового экрана. В режиме редактора они не отображаются (вместо них правая панель редактора).
Каждый предмет отображается как иконка в квадратной области фиксированного размера, примерно равного 20x20 пикселей на игровом экране (но выводится в hi-res). Размер спрайта предмета при этом автоматически масштибируется так, чтобы он полностью помещался в эту область, сохраняя пропорции.
Квадратные иконки располагаются в колонку сверху вниз, с небольшим промежутком между ними. Если весь ряд по высоте заполнен, то начинается новый ряд справа от него с небольшим промежутком.

### Режим просмотра предмета

Пользователь может кликать на иконки предметов. В качестве альтернаивы можно использовать команду EXAMINE для предмета из инвентаря. При этом включается режим просмотра предмета, являющийся разновидностью Subscene. В этом режиме, как при активации Subscene, игровой экран заблюривается/затемняется и в центре его отображается увеличенное изображение предмета. Кликнув за пределами предмета можно выйти из режима просмотра. Кликнув на другой предмет инвентарч пользователь переключает режим просмотра на этот другой предмет.
Важным отличием режима просмотра предмета является то, что предмет выводится поверх игрового экрана, в hi-res, и не подвергается CRT фильтрации.
