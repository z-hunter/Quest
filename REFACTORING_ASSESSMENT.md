# Оценка рефакторинга: Перенос UI редакторов в React

## 📊 Общий статус: **Частично успешно, но с архитектурными компромиссами**

---

## ✅ Что улучшилось

### 1. **Разделение ответственности**
- **До**: `SceneEditor.ts` (~2277 строк) содержал всю UI-логику, DOM-манипуляции, обработку событий и бизнес-логику редактора
- **После**: 
  - React-компоненты (`HierarchyPanel`, `PropertiesPanel`, `EditorToolbar`, `EditorBottomMenu`) отвечают за отображение UI
  - `SceneEditor.ts` всё ещё большой (~2323 строки), но **значительно меньше DOM-манипуляций** (78 упоминаний `getElementById`/`addEventListener` против ~200+ ранее)
  - Появился централизованный store (`editorStore.ts` с zustand) для управления состоянием редактора

### 2. **Декларативный UI вместо императивного**
- **До**: Всё управление списком объектов, панелью свойств, кнопками происходило через `document.getElementById` и прямые манипуляции DOM
- **После**: 
  - `HierarchyPanel` декларативно рендерит список объектов на основе данных из `Game.instance.sceneManager.currentScene`
  - `PropertiesPanel` использует React state и `useEffect` для синхронизации с выбранным объектом
  - F-клавиши и кнопки теперь React-компоненты с явными обработчиками

### 3. **Централизованное состояние редактора**
- Введён `useEditorStore` (zustand) для:
  - `enabled` / `spriteEditorEnabled` — состояние редакторов
  - `selectedObjectId` / `selectedObjectType` — выбранный объект
  - `hierarchyVersion` / `objectVersion` / `spriteVersion` — сигналы для принудительного обновления React-компонентов
  - `mode` — режим редактора (SELECT, DRAW_WALKBOX, DRAW_TRIGGER)
- Это позволяет React-компонентам реагировать на изменения без прямого обращения к `SceneEditor`

### 4. **Улучшенная структура компонентов**
- Чёткое разделение:
  - `components/editor/` — компоненты редактора сцены
  - `components/tools/` — компоненты редактора спрайтов
  - `store/` — глобальное состояние
- `App.tsx` теперь управляет layout редакторов через условный рендеринг на основе `useEditorStore`

### 5. **Меньше глобальных слушателей**
- **До**: Множество `document.addEventListener` для каждого UI-элемента
- **После**: 
  - React-компоненты используют стандартные `onClick`, `onChange` handlers
  - Глобальные слушатели остались только для:
    - Горячих клавиш (F1-F9, Ctrl+S, Ctrl+Z и т.д.) — логично, т.к. они должны работать глобально
    - Обработки мыши на canvas (для drag&drop, рисования полигонов) — тоже логично

## ⚠️ Архитектурные проблемы и компромиссы

### 1. **Паттерн `Game.instance` — глобальный синглтон**
**Проблема**: React-компоненты напрямую обращаются к `Game.instance.editor`, `Game.instance.sceneManager`, `Game.instance.settings`:

```typescript
// Примеры из кода:
const scene = Game.instance?.sceneManager?.currentScene;
Game.instance.editor.startCreating(type);
Game.instance.editor.deleteSelectedObject();
Game.instance.openFileBrowser(...);
```

**Последствия**:
- ❌ Нарушает принципы dependency injection и тестируемости
- ❌ Создаёт скрытые зависимости (компонент неявно зависит от `Game`)
- ❌ Усложняет мокирование для unit-тестов
- ❌ Риск race conditions при инициализации (если компонент рендерится до создания `Game.instance`)

**Рекомендация**: Ввести фасад/контекст:
```typescript
// Вместо Game.instance.editor.startCreating(type)
// Использовать:
const { editor } = useGameContext(); // React Context
editor.startCreating(type);
```

### 2. **Смешанная модель данных: React state + прямая мутация объектов**
**Проблема**: `PropertiesPanel` использует гибридный подход:
- Читает данные из `Game.instance.editor.selectedObject` (прямой доступ к объектам движка)
- Мутирует объекты напрямую: `realObj[field] = value`
- Дублирует состояние в локальный React state: `setObj({ ...obj })`

```typescript
// Из PropertiesPanel.tsx:
const handleChange = (field: string, value: any) => {
    // 1. Мутируем реальный объект напрямую
    realObj[field] = value;
    // 2. Обновляем локальный React state
    obj[field] = value;
    setObj({ ...obj });
    // 3. Сигнализируем store
    incrementObjectVersion();
}
```

**Последствия**:
- ❌ Двойное состояние (React state + объекты движка) может рассинхронизироваться
- ❌ Прямая мутация нарушает принципы React (immutability)
- ❌ Сложно отследить источник изменений (кто и когда изменил объект?)

**Рекомендация**: Ввести слой абстракции:
- Методы `SceneEditor.updateObject(id, patch)` вместо прямой мутации
- React-компоненты вызывают эти методы, а не трогают объекты напрямую
- Или использовать immutable обновления через immer/immutable.js

### 3. **Сигналы через версионирование вместо реактивности**
**Проблема**: Для синхронизации React с данными движка используется паттерн "version bumping":

```typescript
// SceneEditor делает:
useEditorStore.getState().incrementHierarchyVersion();
useEditorStore.getState().incrementObjectVersion();

// PropertiesPanel слушает:
useEffect(() => {
    // Перечитывает данные из Game.instance.editor.selectedObject
}, [selectedObjectId, hierarchyVersion, objectVersion]);
```

**Последствия**:
- ⚠️ Не идеально: React не знает, **что именно** изменилось, только что "что-то изменилось"
- ⚠️ Может приводить к лишним ре-рендерам (если изменился не выбранный объект, а другой)
- ✅ Но работает и проще, чем полная реактивность через Proxy/Observable

**Альтернатива**: Использовать более явные события или реактивные библиотеки (mobx, valtio), но это усложнит архитектуру.

### 4. **SceneEditor всё ещё "god-object"**
**Статус**: `SceneEditor.ts` всё ещё ~2323 строки и содержит:
- Обработку мыши/клавиатуры
- Логику создания/удаления объектов
- Сериализацию/десериализацию сцен
- Undo/redo
- Drag&drop
- Рисование полигонов
- Рендеринг на canvas (walkbox overlay)

**Улучшение**: По сравнению с "до рефакторинга", убрана большая часть UI-логики (DOM-манипуляции), но бизнес-логика редактора всё ещё монолитна.

**Рекомендация**: Разбить на модули:
- `SceneEditorCore` — базовые операции (create/delete/select)
- `SceneEditorIO` — save/load/undo
- `SceneEditorCanvas` — рендеринг и обработка мыши на canvas
- `SceneEditorGeometry` — работа с полигонами

### 5. **Отсутствие типизации в критических местах**
**Проблема**: Много `any` типов:
```typescript
// Из PropertiesPanel.tsx:
const [obj, setObj] = useState<any>(null);
let realObj: any = null;
```

**Последствия**:
- ❌ Нет автодополнения в IDE
- ❌ Ошибки типов обнаруживаются только в runtime
- ❌ Сложнее рефакторить

**Рекомендация**: Ввести интерфейсы:
```typescript
interface EntitySnapshot {
    name: string;
    type: 'Entity' | 'Actor' | 'Static';
    x: number;
    y: number;
    // ...
}
```

## 🎯 Достигнуты ли цели рефакторинга?

### ✅ **Достигнуто:**
1. **Убраны прямые DOM-манипуляции из большей части UI** — React-компоненты управляют отображением
2. **Декларативный UI** — список объектов, панель свойств, кнопки теперь React-компоненты
3. **Централизованное состояние** — zustand store для состояния редактора
4. **Улучшена структура** — компоненты разделены по папкам, App.tsx управляет layout

### ⚠️ **Частично достигнуто:**
1. **Разделение "движок ↔ UI"** — есть, но через глобальный `Game.instance` вместо фасада
2. **Уменьшение размера SceneEditor** — UI-логика убрана, но бизнес-логика осталась монолитной
3. **Типизация** — улучшена в React-компонентах, но остались `any` в критических местах

### ❌ **Не достигнуто:**
1. **Полная изоляция React от движка** — компоненты напрямую обращаются к `Game.instance`
2. **Идеальная реактивность** — используется версионирование вместо полной реактивности
3. **Разбиение SceneEditor на модули** — класс всё ещё монолитный

## 🔧 Рекомендации для дальнейшего улучшения

### Приоритет 1 (Критично для поддержки):
1. **Ввести React Context для Game**:
   ```typescript
   const GameContext = createContext<Game | null>(null);
   // В App.tsx:
   <GameContext.Provider value={game}>
   // В компонентах:
   const game = useContext(GameContext);
   ```
   Это уберёт зависимость от `Game.instance` и улучшит тестируемость.

2. **Типизировать объекты редактора**:
   - Создать интерфейсы `EntitySnapshot`, `SceneSnapshot`, `WalkboxSnapshot`
   - Убрать `any` из `PropertiesPanel` и других компонентов

### Приоритет 2 (Желательно):
3. **Ввести фасад для операций редактора**:
   ```typescript
   interface EditorFacade {
       createObject(type, params): void;
       updateObject(id, patch): void;
       deleteObject(id): void;
       selectObject(id): void;
   }
   ```
   React-компоненты будут вызывать методы фасада, а не напрямую `Game.instance.editor.*`

4. **Разбить SceneEditor на модули** (как описано выше)

### Приоритет 3 (Опционально):
5. **Использовать более реактивный подход** (mobx, valtio) вместо версионирования
6. **Добавить unit-тесты для React-компонентов** (сейчас сложно из-за зависимости от `Game.instance`)
